Security

Rehearsal assumes the agent can be fooled and the data it reads can be hostile. Its job is to make sure neither can change live data without a person seeing exactly what would happen.

Threats and how each is handled

Known limits

We would rather say these plainly than have a reviewer find them.

  • Single writer during replay. Rehearsal assumes nothing else writes to live data during the fraction of a second a replay takes. Production use would add an app side lock or idempotency keys.
  • SQLite today. Shadow copies and diffs use SQLite. Other databases need a different snapshot method.
  • Names typed on the shared link are self reported. The launch token proves a request came from the console, not who sat at it. Reviewer links carry their holder's name, which is why two person approval only trusts them. A real deployment would sit behind single sign on.
  • Effects outside the database. Rehearsal sees what changes in the app's database. If an endpoint also sends an email or charges a card by itself, that happens on the private copy too, so such an app should point its copies at test accounts.
  • The newest audit entries. Removing entries from the end of the log does not break the chain. Production use would also copy the log to append only storage.
  • Prompt Guard sends text to Groq. When a Groq key is set, the text of tool results, customer messages included, is scored there. Set REHEARSAL_PROMPT_GUARD=0 or run fully offline to keep it on your machine.
  • Rules, not mind reading. Risk rules catch effects that look unusual. A harmful change that looks exactly like normal work still needs a careful reviewer, which is why every change is shown in full.
  • A reply applied by the trust policy cannot be unsent in a real system. In the demo store a reply is a row; in production it might be an email. The policy only lets through work with no flag at all, but a reply could still promise something without naming an amount. Set auto_apply = "none" if every reply must be read by a person.
  • Prompt Guard is advisory. It caught blatant injections in testing and missed the polite one in our demo, scoring it 0.14. That is exactly why it never decides anything on its own.
