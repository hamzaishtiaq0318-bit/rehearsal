Security

Rehearsal assumes the agent can be fooled and the data it reads can be hostile. Its job is to make sure neither can change live data without a person seeing exactly what would happen.

Threats and how each is handled

Threat model
ThreatWhat Rehearsal doesTested
Prompt injection hidden in data the agent readsEvery effect is rehearsed first and judged by what would change, not by the words that caused it. Prompt Guard adds an advisory flag and warns the agent.Yes
Mass changes that each look reasonableRules flag tasks that touch several customers, move large sums or change many rows. High risk approvals need an explicit acknowledgement.Yes
Path injection through tool argumentsPath arguments must be plain identifiers of the right type, so 1/orders or ../admin never reach the app.Yes, 13 patterns
Destructive or bulk export endpointsOnly allow listed endpoints become tools. Customer export and permanent delete are never exposed.Yes
Model keys leaking to generated codeThe generated MCP server starts with only its base URL in its environment.Yes
Live data changing during reviewApproval re checks live against the snapshot and refuses if anything moved.Yes
A replay that fails or differsLive is restored from the pre approval snapshot and the restore is verified, with a clear warning if it cannot be.Yes
A runaway agentA hard limit on tool calls per task, enforced even inside a single model reply.Yes
Approvals forged from another websiteWrites need a per launch token and a JSON body, and requests for other host names are refused, which stops DNS rebinding.Yes
Tampering with the recordThe audit log is hash chained; any edit breaks the chain and the console says so.Yes

Known limits

We would rather say these plainly than have a reviewer find them.

  • Single writer during replay. Rehearsal assumes nothing else writes to live data during the fraction of a second a replay takes. Production use would add an app side lock or idempotency keys.
  • SQLite today. Shadow copies and diffs use SQLite. Other databases need a different snapshot method.
  • Reviewer names are self reported. The launch token proves a request came from the console, not who sat at it. A real deployment would sit behind single sign on.
  • Rules, not mind reading. Risk rules catch effects that look unusual. A harmful change that looks exactly like normal work still needs a careful reviewer, which is why every change is shown in full.
  • Prompt Guard is advisory. It caught blatant injections in testing and missed the polite one in our demo, scoring it 0.14. That is exactly why it never decides anything on its own.
